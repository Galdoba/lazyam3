# Шпаргалка: выбор архитектурных решений под домен

Документ для разработчика, который скопировал шаблон и начинает адаптировать его под конкретный проект. Каждый раздел — один вопрос, варианты ответа, критерии выбора.

Читать сверху вниз. Решения связаны: ответ на вопрос 1 влияет на 3 и 6, ответ на 2 — на 3 и 4. Если меняешь одно решение, перечитай соседние.

---

## Вопрос 1. Разделять ли handler (команду) и usecase?

**Что это значит.** Handler — код в `Action`, который парсит флаги и вызывает логику. Usecase — отдельная функция/структура, которая принимает DTO и делает работу. Вопрос: оставляем логику в `Action` или выносим в `internal/usecase/`.

### Вариант A. Логика остаётся в `Action`

Команда сама читает флаги, дёргает модули, форматирует вывод.

```go
Action: func(ctx context.Context, cmd *cli.Command) error {
    key := cmd.String("key")
    store, _ := modules.Store()
    // ... логика ...
    fmt.Fprintf(cmd.Root().Writer, ...)
    return nil
}
```

**Когда подходит:**
- В приложении 1–5 команд.
- Каждая команда — уникальный сценарий, не пересекающийся с другими.
- Логика тривиальна: 10–30 строк на команду.
- Нет планов на HTTP/gRPC/второй адаптер.
- Нет планов на тесты сценария отдельно от CLI.
- Скорость разработки важнее долгосрочной структуры.

**Цена:**
- Логику нельзя переиспользовать.
- Нельзя протестировать сценарий без запуска CLI.
- При росте приложения `Action` пухнет, флаги перемешиваются с логикой.
- Рефакторинг в usecase позже будет болезненным, если команд станет 20+.

### Вариант B. Логика вынесена в usecase

Команда — тонкий адаптер: парсинг → вызов → рендер. Usecase — отдельная структура с методами.

```go
// commands/cmd1.go
Action: func(ctx context.Context, cmd *cli.Command) error {
    out, err := uc.Increment(ctx, usecase.IncrementInput{
        Key:   cmd.String("key"),
        Delta: cmd.Int("delta"),
    })
    if err != nil { return err }
    return presenter.Render(out)
}

// usecase/increment.go
func (u *Increment) Execute(ctx context.Context, in IncrementInput) (IncrementOutput, error) { ... }
```

**Когда подходит:**
- Команд больше 5, или планируется рост.
- Один и тот же сценарий используется в нескольких командах (например, `app sync` и `app sync --dry-run`).
- Сценарий переиспользуется в TUI (команда `cmd3` в шаблоне — уже звоночек).
- Планируется HTTP-адаптер или программный API.
- Логика сценария больше 30–50 строк.
- Есть требования к тестируемости без CLI.
- Сценарий состоит из нескольких шагов над несколькими портами.

**Цена:**
- Больше файлов, больше boilerplate (DTO, конструкторы, интерфейсы).
- Нужно решить вопросы 3 и 4 (где порты, что с presentation).
- Для тривиальных команд выглядит избыточно.

### Критерий выбора

| Признак | A | B |
|---------|---|---|
| Команд ≤ 5 и не будет роста | ✓ | |
| Команд > 5 или рост планируется | | ✓ |
| Сценарий повторяется в 2+ местах | | ✓ |
| Есть TUI или HTTP | | ✓ |
| Логика > 50 строк на сценарий | | ✓ |
| Нужны тесты сценария | | ✓ |
| Только CLI, только сейчас | ✓ | |

**Гибрид.** Можно начать с A и выносить в B **точечно** — только те сценарии, которые переиспользуются или сложны. Не обязательно выносить всё сразу.

## Вопрос 2. Один bounded context или несколько?

**Что это значит.** Bounded context — это область предметной области со своим языком и своими правилами. Вопрос: кладём ли домен и usecase в один плоский пакет или разбиваем на несколько контекстов.

### Вариант A. Один контекст (плоско)

```
internal/
  domain/
    entity.go
    errors.go
    rules.go
  usecase/
    increment.go
    sync.go
    export.go
```

**Когда подходит:**
- Домен описывается одним-двумя понятиями (например, «счётчик» или «файл»).
- Все сценарии используют одни и те же сущности.
- Термины не конфликтуют (нет двух разных «Item» в разных смыслах).
- Команда разработки — 1–2 человека.
- Приложение решает одну задачу.

**Цена:**
- При росте домена пакет превращается в свалку.
- Термины разных областей начинают конфликтовать (например, `User` в аутентификации и `User` в отчётности — разные вещи).
- Границы между областями размываются.

### Вариант B. Несколько контекстов

```
internal/
  domain/
    counter/
      entity.go
    catalog/
      entity.go
  usecase/
    counter/
      increment.go
    catalog/
      import.go
```

**Когда подходит:**
- В домене есть 2+ независимые области со своими понятиями.
- У областей разные жизненные циклы (одна стабильна, другая в разработке).
- Разные команды/разработчики работают над разными областями.
- Есть пересечения сущностей, но с разным смыслом.
- Планируется выделение контекста в отдельный сервис.

**Цена:**
- Дублирование кода, если сущности пересекаются.
- Нужно решать, где живут общие типы (в `shared/` или `common/`).
- Больше файлов, сложнее навигация.
- Для маленького приложения — оверинжиниринг.

### Критерий выбора

| Признак | A (один) | B (несколько) |
|---------|----------|---------------|
| Домен — 1–2 понятия | ✓ | |
| Домен — 3+ независимых области | | ✓ |
| Термины не конфликтуют | ✓ | |
| Термины конфликтуют между областями | | ✓ |
| Команда 1–2 человека | ✓ | |
| Команда 5+ человек | | ✓ |
| Приложение решает одну задачу | ✓ | |
| Приложение — платформа с модулями | | ✓ |

**Правило большого пальца.** Начни с A. Разделяй, когда почувствуешь, что в `domain/` лежат сущности, которые не должны знать друг о друге. Не разделяй заранее — преждевременное разделение хуже, чем позднее.

## Вопрос 3. Где живут порты (интерфейсы)?

**Что это значит.** Порты — интерфейсы, которые usecase требует от инфраструктуры (`Store`, `Cache`, `Clock`, `HTTPClient`). Вопрос: объявляем их в usecase, в отдельном пакете, или в адаптерах.

### Вариант A. Порты в usecase (consumer-side)

Интерфейс объявлен в том пакете, который его потребляет.

```go
// usecase/counter/ports.go
package counter

type Store interface {
    Get(ctx context.Context, key string) (any, bool)
    Set(ctx context.Context, key string, value any) error
}
```

**Когда подходит:**
- Каждый usecase-пакет имеет свой небольшой набор портов.
- Порты узкие (2–4 метода).
- Один и тот же `Store` может быть нужен в разном виде разным сценариям.
- Хочется избежать «общего» пакета портов.

**Цена:**
- Если один и тот же порт нужен в нескольких usecase, он дублируется.
- Нет единого места, где видно все порты приложения.

**Это правило Go-сообщества: «интерфейсы объявляются там, где используются».**

### Вариант B. Порты в отдельном пакете `internal/ports/`

Все интерфейсы в одном месте.

```go
// ports/store.go
package ports

type Store interface { ... }
type Cache interface { ... }
type Clock interface { ... }
```

**Когда подходит:**
- Порты многочисленны (10+).
- Один порт используется во многих usecase.
- Хочется видеть полную картину зависимостей приложения.
- Есть договорённость в команде, что порты — «публичный контракт» приложения.

**Цена:**
- Пакет `ports` импортируется везде — становится «слабым» пакетом с высокой связанностью.
- Порты отчуждаются от тех, кто их потребляет.
- Соблазн сделать порт «на все случаи» — широким и неудобным.

### Вариант C. Порты в адаптерах (провайдер-сайд)

Интерфейс объявлен в пакете адаптера.

```go
// adapters/storage/jsonstore/store.go
package jsonstore

type Store interface { ... }
type jsonStore struct { ... }
```

**Когда подходит:**
- Почти никогда.
- Может быть оправдано, если адаптер — сторонняя библиотека, и мы просто «оборачиваем» её интерфейс.

**Цена:**
- Usecase зависит от пакета адаптера — нарушение направления зависимостей.
- Нельзя подменить реализацию без правки usecase.
- Это антипаттерн для чистой архитектуры.

### Критерий выбора

| Признак | A (в usecase) | B (в ports/) | C (в адаптере) |
|---------|---------------|--------------|----------------|
| Портов ≤ 5 | ✓ | | |
| Портов > 10 | | ✓ | |
| Порт используется в 1 usecase | ✓ | | |
| Порт используется в 5+ usecase | | ✓ | |
| Команда маленькая | ✓ | | |
| Хочется видеть все контракты сразу | | ✓ | |
| Адаптер — сторонняя библиотека | | | ✓ (редко) |
| Всё остальное | ✓ (по умолчанию) | | |

**Правило большого пальца.** Начни с A. Переходи к B, когда увидишь, что один и тот же интерфейс дублируется в 3+ usecase, или когда портов станет больше 10.

## Вопрос 4. Является ли presentation портом?

**Что это значит.** Presentation — то, что превращает результат сценария в вывод для пользователя (TUI, JSON, plain text, silent). Вопрос: возвращает ли usecase готовый к печати результат, или возвращает DTO, а presentation — отдельная сущность.

### Вариант A. Usecase возвращает DTO, presentation — отдельно

```go
// usecase возвращает структуру
type IncrementOutput struct { Key string; Value float64 }

// presentation рендерит
type Presenter interface { Render(w io.Writer, out IncrementOutput) error }

// команда связывает
out, _ := uc.Increment(ctx, in)
return presenter.Render(cmd.Root().Writer, out)
```

**Когда подходит:**
- Есть или планируется `--output json|yaml|plain|table`.
- Один сценарий используется в CLI и TUI/HTTP.
- Нужны тесты сценария без проверки строк вывода.
- Presentation варьируется в зависимости от контекста.

**Цена:**
- Больше кода: DTO + Presenter для каждой команды.
- Нужно решать, где живёт DTO (в usecase или отдельно).
- При тривиальных командах выглядит избыточно.

### Вариант B. Usecase сам форматирует вывод

```go
// usecase возвращает строку
func (u *Increment) Execute(ctx context.Context, in IncrementInput) (string, error) {
    // ...
    return fmt.Sprintf("%s = %v\n", key, next), nil
}
```

**Когда подходит:**
- Только CLI, только plain text.
- Формат вывода фиксирован и не будет меняться.
- Один сценарий — одна команда.
- Простота важнее гибкости.

**Цена:**
- Формат вывода вшит в логику — тестировать надо через парсинг строк.
- Нельзя переиспользовать сценарий в TUI/HTTP.
- `--output` флаги добавить больно.

### Вариант C. Гибрид: usecase возвращает DTO, команда форматирует

```go
out, _ := uc.Increment(ctx, in)
fmt.Fprintf(cmd.Root().Writer, "%s = %v\n", out.Key, out.Value)
```

**Когда подходит:**
- DTO уже нужен для других целей.
- Формат вывода привязан к команде, не к сценарию.
- Не хочется вводить `Presenter` как отдельный тип.

**Цена:**
- Форматирование размазано по командам.
- Дублирование логики рендера между командами.
- При появлении `--output` придётся рефакторить.

### Критерий выбора

| Признак | A (Presenter) | B (в usecase) | C (в команде) |
|---------|---------------|---------------|---------------|
| Несколько форматов вывода | ✓ | | |
| Только plain text | | ✓ | |
| Сценарий в CLI + TUI/HTTP | ✓ | | |
| Один сценарий — одна команда | | ✓ | ✓ |
| Нужны тесты сценария | ✓ | | ✓ |
| Команд 1–3, всё просто | | ✓ | ✓ |
| Команд > 5 | ✓ | | |
| Планируется `--output` | ✓ | | |

**Правило большого пальца.** Начни с B для тривиальных команд (1–3). Переходи к C, когда сценариев станет больше и захочется единообразия. Переходи к A, когда появится второй формат вывода или второй адаптер (TUI/HTTP).

## Вопрос 5. Направление зависимостей

**Что это значит.** Кто кого импортирует. Вопрос: соблюдаем ли мы строгое правило «зависимости внутрь» или допускаем отступления.

### Вариант A. Строгое правило: `commands → usecase → domain`, `usecase → ports ← adapters`

- `domain` не импортирует ничего, кроме stdlib.
- `usecase` импортирует `domain` и объявляет порты.
- `adapters` импортируют порты (или реализуют их структурно).
- `commands` импортируют `usecase` и `presentation`.
- `app` (контейнер) импортирует всё — это composition root.

**Когда подходит:**
- Проект с доменом, где важны инварианты.
- Планируется рост и переиспользование.
- Команда знакома с чистой архитектурой.
- Есть тесты домена и usecase.

**Цена:**
- Больше интерфейсов и конструкторов.
- Иногда «через порт» выглядит избыточно для тривиальной операции.
- Требует дисциплины.

### Вариант B. Прагматичное отступление: usecase импортирует адаптер напрямую

```go
// usecase/counter/increment.go
import "internal/adapters/storage/jsonstore"

type Increment struct { store *jsonstore.Store }
```

**Когда подходит:**
- В проекте один адаптер, и он не будет меняться.
- Хочется избежать интерфейса ради интерфейса.
- Прототип, MVP, сроки поджимают.
- Нет тестов, где нужна подмена адаптера.

**Цена:**
- Usecase зависит от конкретной реализации.
- Замена адаптера (JSON → SQLite) ломает usecase.
- Тесты требуют реального адаптера или моков на уровне пакета.
- Направление зависимостей нарушено — «грязь» копится.

### Вариант C. Смешанный: домен — чисто, usecase — прагматично

`domain` строго чистый, `usecase` может импортировать адаптеры напрямую, если порт избыточен.

**Когда подходит:**
- Домен действительно важен (инварианты, тесты).
- Инфраструктура простая и стабильная.
- Хочется баланс между чистотой и простотой.

**Цена:**
- Непоследовательность: где-то порт, где-то прямой импорт.
- Нужно каждый раз решать: порт или прямой импорт?

### Критерий выбора

| Признак | A (строго) | B (прагматично) | C (смешанно) |
|---------|-----------|-----------------|--------------|
| Домен с инвариантами | ✓ | | ✓ |
| Прототип/MVP | | ✓ | |
| Один адаптер навсегда | | ✓ | |
| 2+ адаптера на один порт | ✓ | | ✓ |
| Нужны тесты usecase | ✓ | | ✓ |
| Команда знакома с ЧА | ✓ | | |
| Сроки поджимают | | ✓ | |
| Всё остальное | ✓ | | |

**Правило большого пальца.** Для проектов с доменом — A. Для CLI-утилит без домена — B. Для средних — C, но с явным правилом: «домен всегда чист, usecase может отступать, если порт избыточен».

## Вопрос 6. Что делает команда с ошибкой?

**Что это значит.** Ошибка возникает в usecase или адаптере. Вопрос: как она превращается в exit code и сообщение пользователю.

### Вариант A. Все ошибки одинаковы

`Action` возвращает ошибку как есть, `main.go` логирует и выходит с кодом 1.

```go
if err := root.Run(ctx, os.Args); err != nil {
    logger.Error("execution failed", "error", err)
    return 1
}
```

**Когда подходит:**
- CLI-утилита без сложной обработки ошибок.
- Пользователь — разработчик, ему важен стектрейс.
- Нет требований к разным exit code.
- Нет автоматизации поверх CLI (CI, скрипты, оркестраторы).

**Цена:**
- Нельзя отличить «неверный ввод» от «баг».
- CI не может по-разному реагировать на разные ошибки.
- Пользователь не понимает, что делать.

### Вариант B. Классы ошибок с разными exit code

Определяем классы: `UserError` (exit 2), `ConfigError` (exit 3), `SystemError` (exit 1). Команда маппит доменную ошибку в класс.

```go
type UserError struct { msg string }
func (e UserError) Error() string { return e.msg }

// в main.go
switch {
case errors.As(err, &UserError{}):
    fmt.Fprintln(os.Stderr, err)
    return 2
default:
    logger.Error("execution failed", "error", err)
    return 1
}
```

**Когда подходит:**
- CLI используется в скриптах и CI.
- Есть пользовательские ошибки, которые надо печатать без стектрейса.
- Есть конфигурационные ошибки, которые надо отличать от багов.
- Есть требования к exit code (например, `grep`-подобное поведение: 1 = не найдено, 2 = ошибка).

**Цена:**
- Нужно определить классы и договориться о маппинге.
- Usecase должен возвращать типизированные ошибки.
- Больше кода в `main.go` и командах.

### Вариант C. Типизированные доменные ошибки без exit code

Домен возвращает `domain.ErrNotFound`, `domain.ErrInvalidDelta`. Команда решает, как их показать, но exit code всегда 1.

**Когда подходит:**
- Домен важен, но CLI — единственный потребитель.
- Разные сообщения пользователю нужны, разные exit code — нет.
- Тесты домена проверяют `errors.Is`.

**Цена:**
- Скрипты не могут отличить типы ошибок.
- Полумера между A и B.

### Критерий выбора

| Признак | A (одинаково) | B (классы + exit) | C (типизированные, один exit) |
|---------|--------------|-------------------|-------------------------------|
| Только человек-пользователь | ✓ | | |
| CLI в скриптах/CI | | ✓ | |
| Домен с инвариантами | | | ✓ |
| Нужны разные exit code | | ✓ | |
| Нужны разные сообщения | | ✓ | ✓ |
| Прототип | ✓ | | |
| Продакшен-инструмент | | ✓ | |

**Правило большого пальца.** Начни с A. Переходи к C, когда появится домен с типизированными ошибками. Переходи к B, когда CLI начнут использовать в скриптах и понадобятся разные exit code.

| 4 | Presentation | Usecase форматирует | Команда форматирует | Presenter как порт |
| 5 | Зависимости | Прагматично | Домен чист, usecase прагматичен | Строго |
| 6 | Ошибки | Одинаково | Типизированные доменные | Классы + exit code |

**Как пользоваться.** Определи, к какому столбцу ближе твой проект **сейчас**, и принимай решения по этому столбцу. Не заглядывай в «сложный», если проект пока простой — преждевременная сложность хуже, чем поздний рефакторинг.

---

## Как принимать решения, если проект «посередине»

1. **Начни с простого столбца.** Для каждого вопроса выбери самый простой вариант.
2. **Зафиксируй триггеры перехода.** Например: «когда команд станет 6 — выносим usecase», «когда появится `--output json` — вводим Presenter», «когда CLI начнут использовать в CI — вводим exit code».
3. **Пересматривай по триггеру, не заранее.**
4. **Записывай решения.** Одно-два предложения в `docs/decisions.md`: «Почему сейчас A, при каком условии перейдём к B». Это спасает от повторного обсуждения.

---

## Чего в шпаргалке нет

Эти вопросы **не решаются до появления домена** и в шаблоне не должны быть предрешены:

- Нужны ли агрегаты и события.
- Есть ли транзакции и как их границы соотносятся с usecase.
- Нужен ли CQRS (разделение чтения и записи).
- Есть ли сага/процесс-менеджер для длинных сценариев.
- Нужен ли outbox для надёжной публикации событий.

Каждый из этих вопросов — отдельное архитектурное решение, которое появляется **только когда домен это потребует**. Шаблон не должен их предполагать.
